# 2026-08-22 일일 개발 리포트

> 집계 시간: 2026-08-22 09:00 ~ 2026-08-23 09:00

## 오늘의 목표

- WeaponComponent의 PlayerCharacter·Projectile 생성 의존성 제거
- PhysicalProjectile, Hitscan, Beam을 지원하는 공격 전달 구조 구현
- 탄약 소비와 공격 실행을 Attack Commit 이벤트 기반으로 분리
- Projectile Pool과 Beam Effect 관리 기반 추가

## 완료한 작업

### 1. 공격 전달 구조 확정

- 별도 `HitscanExecutorComponent`, `BeamExecutorComponent`는 만들지 않기로 함.
- `WeaponComponent`가 `EAttackDeliveryType`을 기준으로 PhysicalProjectile, Hitscan, Beam을 분기하도록 함.
- PhysicalProjectile은 생성 요청 이벤트를 PlayerCharacter에 전달하고 ProjectileFactorySubsystem이 실행하도록 함.
- Hitscan은 WeaponComponent가 Line Trace와 즉시 명중 결과를 계산하도록 함.
- Beam은 WeaponComponent가 지속 Trace와 공격 상태를 관리하고 시각 효과 요청만 외부로 전달하도록 함.
- WeaponComponent는 공격 대상의 `FHitResult`와 Actor를 일시적으로 다룰 수 있지만 발사자 PlayerCharacter·Pawn·Controller 참조는 저장하지 않도록 경계를 정함.

### 2. WeaponComponent 리팩터링

- `OwnerCharacter`, `GetOwner()` 기반 게임 로직, `ACharacter`, `APawn`, Controller 의존성을 제거함.
- 탄약 직접 차감과 `SpawnActorDeferred()` 기반 Projectile 직접 생성을 제거함.
- Player가 전달한 조준 목표를 저장하고 Fire 시작 전에 Aim Solution을 고정하도록 함.
- `Weapon_FireCommit` 시점의 현재 Muzzle 위치에서 고정된 목표점까지의 발사 방향을 다시 계산하도록 함.
- Hitscan·Beam Trace, 지속 공격 시간, Tick 횟수, 탄약 비용 증가 및 피해 증가 상태를 관리하도록 확장함.
- WeaponComponent 자체 Tick은 추가하지 않음.
- 공격 확정 정보와 완료 결과를 이벤트로 전달하도록 정리함.

### 3. PlayerCharacter 중재 구조 구현

- `OnWeaponAttackCommitted` 이벤트를 PlayerCharacter가 수신하도록 연결함.
- 현재 단계에서는 PlayerCharacter가 WeaponComponent에 탄약 차감을 요청하도록 함.
- 향후 Inventory 도입 시 동일한 중재 위치에서 InventoryComponent에 탄약 아이템 소비를 요청할 수 있도록 경계를 유지함.
- PhysicalProjectile 요청은 ProjectileFactorySubsystem으로 전달하도록 함.
- Hitscan·Beam 결과에는 공격 주체인 Player를 추가하여 피해 처리 흐름으로 전달하도록 함.
- Beam Effect 요청은 CombatEffectSubsystem으로 전달하도록 함.
- 탄약, 장착, Fire/Reload 완료 및 반동 이벤트를 PlayerCharacter에서 수신하도록 구성함.

### 4. Projectile Pool 구현

- PhysicalProjectile 전용 `UProjectileFactorySubsystem`을 추가함.
- Pool에 사용 가능한 Actor가 없을 때만 `SpawnActorDeferred()`를 실행하도록 함.
- `AProjectileController`가 `Destroy()`와 `SetLifeSpan()` 대신 충돌 또는 Lifetime 종료 시 Pool로 반환되도록 변경함.
- Pool에서 재사용할 때 발사체 데이터를 다시 적용하고 Owner·Instigator를 Factory에서 지정하도록 함.
- ProjectileDataAsset은 속도, 수명, 중력, 충돌 크기, Mesh와 충돌 효과 등 정적 비행 데이터만 보관하도록 정리함.
- 이 단계에서는 단일 C++ ProjectileController 풀 구조로 단순화함.

### 5. Beam Effect 관리 기반 추가

- `UCombatEffectSubsystem`을 추가함.
- Beam Niagara 생성, 갱신 및 종료만 담당하도록 제한함.
- Trace, 탄약, 피해 계산은 WeaponComponent 책임으로 유지함.

### 6. 공격·탄약 데이터 확장

- 공통 Attack Commit 데이터 구조를 추가함.
- WeaponDataAsset에 DeliveryType, ShootType 및 단발·지속 공격용 탄약 비용과 증가 규칙을 반영함.
- WeaponModel이 현재 장전량과 무기 인스턴스의 동적 상태를 계속 소유하도록 함.
- PhysicalProjectile, Hitscan, Beam과 SingleShot, RapidFire, ThreeShot, ChargedShot, Continuous를 서로 다른 분류 축으로 유지함.

### 7. 컴파일 오류 수정

- `TObjectPtr`가 `AddIgnoredComponent()`의 여러 오버로드로 암시적 변환되어 발생한 모호성 오류를 확인함.
- `LinkedAnimationMesh.Get()`, `LinkedBodyCollisionComponent.Get()`을 명시적으로 전달하도록 수정함.
- ProjectileController 전방 선언과 `TSubclassOf` 사용에서 발생한 C2027 오류를 분석함.
- 당시 단일 Projectile 풀 설계에 맞춰 ProjectileDataAsset의 ProjectileClass 참조를 제거하고 관련 검사를 정리함.

### 8. GA_WeaponFire 완료 흐름 정리

- `Resolve Weapon Component`는 WeaponComponent 확보를 위해 유지함.
- 완료 이벤트를 받기 위해 PlayerCharacter로 다시 Cast하는 흐름은 제거하도록 함.
- `Fire Equipped Weapon` 반환값은 발사 완료가 아니라 발사 시작 수락 여부임을 명확히 함.
- 성공 즉시 `End Ability`하지 않고 `Event.Weapon.FireFinished` Gameplay Event를 기다린 뒤 Ability를 종료하도록 Blueprint 흐름을 정리함.

### 9. 코드 작성 형식 규칙 반영

- `UPROPERTY` 선언은 `meta`까지 가능한 한 한 줄로 유지하도록 함.
- 짧은 조건식, 함수 호출과 반환문은 불필요하게 여러 줄로 나누지 않도록 함.
- 긴 함수 선언, Delegate, 복잡한 논리 조건과 의미 구분이 필요한 호출만 여러 줄로 작성하도록 함.

## 확정한 설계

- WeaponComponent는 발사자의 구체 Actor 타입과 Projectile 생성 객체를 알지 않음.
- PlayerCharacter는 WeaponComponent, 탄약 소유 객체, 공격 실행 Subsystem 사이의 중재자임.
- PhysicalProjectile만 Factory와 Object Pool을 사용함.
- Hitscan과 Beam의 공격 판정은 WeaponComponent가 담당함.
- CombatEffectSubsystem은 Beam 시각 효과 수명만 관리함.
- Fire Ability는 발사 시작 반환값이 아니라 완료 Gameplay Event를 기준으로 종료함.
- 공격 전달 방식과 발사 시간 방식은 별도 데이터 축으로 유지함.

## 테스트 결과

- 전체 C++ 변경 후 정적 의존성 검사 통과.
- `OwnerCharacter`, Character/Pawn/Controller 및 WeaponComponent 내부 Projectile 생성 의존성 제거 확인.
- `AddIgnoredComponent()`의 TObjectPtr 오버로드 모호성 수정.
- ProjectileClass 제거 후 관련 참조가 남아 있지 않음을 확인함.
- 실제 전체 빌드와 PIE는 Blueprint 재연결이 필요한 상태로 사용자 측에서 진행함.
