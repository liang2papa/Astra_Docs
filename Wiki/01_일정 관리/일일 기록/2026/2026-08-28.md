# 2026-08-28 일일 개발 리포트

> 집계 시간: 2026-08-28 09:00 ~ 2026-08-29 09:00

## 오늘의 목표

- 장비·인벤토리 시스템의 C++ 기반 구조 구현
- Item DataAsset과 런타임 ItemInstance 책임 분리
- 무기 생성·장착 흐름을 ItemInstance Factory 구조와 연결
- Montage가 없는 무기의 Draw 완료 시점 보완
- PlayerCharacter Details 패널 ensure 원인 진단

## 완료한 작업

### 1. Item 공통 정의 구조 구현

- `UItemDataAsset`을 `UPrimaryDataAsset` 기반의 공통 아이템 정적 정의로 정리함.
- Item Category, Rarity, 표시 이름, 설명, 아이콘, 무게, 최대 Stack 수량 등 공통 필드를 구성함.
- Equipment와 Weapon DataAsset이 Item DataAsset 계층을 통해 공통 속성을 상속하도록 정리함.
- 독립적으로 식별·로드해야 하는 아이템 정의는 Primary Asset으로 관리하고, 실제 런타임 객체와 분리하는 방향을 적용함.
- 대형 Mesh·Animation·Sound·VFX 등 콘텐츠 참조는 향후 Soft Reference와 선행 로딩 정책을 함께 검토하도록 구분함.

### 2. ItemInstance 런타임 모델 계층 구현

- `UItemInstance`를 정적 ItemDataAsset을 참조하면서 Runtime Item ID와 Quantity를 관리하는 런타임 객체로 구현함.
- 초기화 여부, 정적 데이터 조회, Runtime ID 조회, 수량 변경과 Stack 가능 여부를 제공하도록 함.
- `UEquipmentInstance`와 `UWeaponInstance`가 ItemInstance 계층을 상속하도록 정리함.
- WeaponInstance가 탄약·내구도·Projectile Class 등 무기별 런타임 상태를 담당하도록 기존 구조와 연결함.
- ItemInstance 자체는 저장 대상이 아니라 SaveData에서 복원되는 레벨 단위 객체라는 설계 방향을 유지함.

### 3. ItemInstanceFactorySubsystem 구현

- 현재 World의 ItemInstance 생성과 Runtime Item ID 발급을 담당하는 `UItemInstanceFactorySubsystem`을 추가함.
- 일반 Item, Equipment, Weapon 정의에 따라 올바른 Instance 타입을 생성하는 API를 구성함.
- Runtime Item ID를 1부터 순차 발급하고 생성 시 초기 수량·탄약·내구도 등 초기 상태를 전달하도록 함.
- 생성 책임은 Factory가 맡고, 생성된 Instance의 강한 참조와 위치는 Inventory·Equipment·ItemBundle이 소유하도록 경계를 정리함.
- 무기 생성 경로가 공통 ItemInstance 계층과 Factory를 사용하도록 연결함.

### 4. InventoryComponent 기본 기능 구현

- PlayerState가 소유하는 `UInventoryComponent`를 추가함.
- 7×7 최대 Grid와 기본 활성 슬롯 21칸을 수용할 수 있는 Capacity 구조를 구현함.
- 슬롯 조회, 빈 슬롯 검색, Item 위치 검색, 활성 슬롯 판정 기능을 추가함.
- Item 추가·제거·이동, Stack 병합·분할, Inventory Compact 기능을 구성함.
- 슬롯 변경, 전체 Inventory 변경, Capacity 변경을 알리는 Blueprint 이벤트를 추가함.
- Capacity 축소 시 활성 범위 안으로 Item을 정리할 수 있는 기반을 마련함.

### 5. Player·Weapon·Subsystem 연결 정리

- `AAstraPlayerState`에 InventoryComponent를 생성하고 플레이어 인벤토리의 소유 위치를 확정함.
- PlayerCharacter와 WeaponComponent의 무기 Instance 생성·장착 흐름을 ItemInstanceFactorySubsystem과 연결함.
- ProjectileFactorySubsystem과 CombatEffectSubsystem의 관련 타입 선언·참조를 현재 구조에 맞게 정리함.
- ProjectileController와 공격 확정 데이터의 타입 연결을 보완함.
- PlayerHUDComponent와 PlayerController의 연동부를 현재 Item·Weapon 타입 구조에 맞게 정리함.

### 6. Montage 없는 무기의 Draw 준비 시간 구현

- WeaponDataAsset에 무기별 `DrawReadyDelay` 설정을 추가함.
- Equip Montage가 없는 경우 무기를 손에 부착한 직후 Draw를 완료하지 않고 지정 시간 동안 Drawing 상태를 유지하도록 함.
- 지연 시간이 끝난 뒤 Draw 진행 상태·Carry State·손 부착 성공 여부를 다시 확인하고 Ready로 전환하도록 함.
- Draw 실패·취소 시 Timer와 Pending Action이 정리되도록 기존 완료 흐름과 연결함.
- AnimBP는 Ready 상태만이 아니라 무기가 손에 들어온 시점부터 무장 자세 블렌딩을 시작해야 한다는 연결 조건을 정리함.

### 7. Draw StateTree 실행 흐름 검토

- `STT_WeaponDrawing`의 Enter·Tick·Exit 흐름을 Blueprint 내보내기로 확인함.
- `ExecuteDrawWeapon()` 성공 시 Task를 즉시 완료하지 않고 Running 상태를 유지하는 현재 구성이 정상임을 확인함.
- Tick에서 `IsDrawInProgress` 종료를 감지한 뒤 마지막 Draw 성공 결과로 Task를 완료하는 흐름을 확인함.
- 문제 원인을 StateTree 조기 종료가 아니라 Montage 부재 시 같은 프레임에 Ready와 Pending Fire가 실행되는 경로로 좁힘.

### 8. PlayerCharacter Details 패널 ensure 진단

- PIE 중 Outliner에서 `BP_PlayerCharacter_C_0` 선택 시 발생하는 `PropertyNodeMap.ParentProperty == CurObjectNode` ensure를 분석함.
- 게임 실행 로직보다 Details 패널이 중첩된 런타임 UObject 참조를 속성 트리로 구성하는 과정의 충돌 가능성이 높다고 판단함.
- PlayerContext, StatusModel, LocomotionComponent, WeaponComponent가 동일 객체를 여러 경로로 노출하는 구조를 확인함.
- 런타임 링크 속성에서 Details 노출 지정자를 제거하는 진단 방향과 새 PlayerCharacter Blueprint 비교 절차를 정리함.
- 기존 Blueprint에서만 재현되면 오래된 SCS·서브오브젝트 직렬화 데이터 문제로 구분하도록 테스트 기준을 마련함.

### 9. WeaponComponent 구조 정리 방향 확정

- WeaponComponent가 Draw·Holster·Aim·Fire·Recoil·Accuracy·Reload를 모두 포함해 구현 파일이 비대해진 상태를 점검함.
- Blueprint API와 StateTree 연결을 유지하기 위해 Component 자체를 여러 개로 나누는 작업은 보류함.
- `UWeaponComponent` 클래스는 유지하면서 Carry, Aim, Fire, RecoilAccuracy, Reload 기능별 `.cpp`로 구현만 분리하는 1차 정리 방향을 확정함.
- 기능 분리는 동작 변경 없이 코드 위치만 이동하는 별도 후속 작업으로 남김.

## 확정한 설계

- ItemDataAsset은 정적 정의, ItemInstance는 레벨 단위 런타임 상태를 담당함.
- ItemInstanceFactorySubsystem이 Instance 생성과 Runtime Item ID 발급을 담당함.
- InventoryComponent는 PlayerState가 소유함.
- 생성된 ItemInstance의 수명과 강한 참조는 Inventory·Equipment·ItemBundle이 관리함.
- Montage가 없는 무기는 손 부착과 Ready·Pending Action 실행 사이에 `DrawReadyDelay`를 둠.
- WeaponComponent는 하나의 Component로 유지하고 필요 시 기능별 구현 파일만 분리함.

## 테스트·검토 결과

- ItemDataAsset·ItemInstance·EquipmentInstance·WeaponInstance 계층과 Factory 연결을 정적 검토함.
- InventoryComponent의 슬롯·Capacity·Stack·Compact API 구성을 확인함.
- STT_WeaponDrawing의 정상·실패·취소 흐름을 검토함.
- DrawReadyDelay의 정상·실패·취소 실행 순서를 정리함.
- PlayerCharacter Details ensure는 단일 속성 수정만으로 해결되지 않아 추가 비교 검증이 필요함.
- Plastic SCM 상태 조회는 인증 실패로 완료하지 못했으며, 로컬 소스 수정 시간과 작업 기록을 기준으로 범위를 확인함.
