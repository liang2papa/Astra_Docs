# 플레이어 연사·빈 탄창 재장전 연결

2026-10-21 재장전 사용자 완료 확인. 사건 기반 AutoReload·Sprint 취소 정책을 현재 기준으로 유지. 재장전 절차는 완료 구성 기록, 연사·반동의 별도 잔여와 구분

> 10/20 제공 StateTree·Blueprint를 바탕으로 실제 입력·전이·GA/Task 계약 보존. 연사·반동은 C++ 반영 후 별도 실행 확인 잔여
> 현재 상태는 [현재 작업 상태](../01_일정%20관리/현재%20작업%20상태.md), NPC 로그·진단은 [NPC 연결·검증](NPC%20연결·검증.md#보존할-확인-결과와-별도-잔여) 참조. 과거 노드 오류를 현재 미수정으로 단정하지 않음

## 2. 현재 입력·참조 경로

```text
BP_PlayerController
├─ IA_Astra_Attack.Triggered → SendControlCommand(AttackStarted)
├─ IA_Astra_Attack.Completed / Canceled → SendControlCommand(AttackCompleted)
└─ IA_Astra_Reload.Started → SendControlCommand(Reload)
   → 조종 Pawn의 HandleControlCommand
   → EntityInputBufferComponent
   → EntityCharacter.Tick → ProcessBufferedWeaponInputs
   → Pressed 입력 소비 → HandleWeaponCommandRequested
   → StateMediator.SendUpperCommand
   → StateTree.Event.UpperCommand + FUpperStateCommandPayload
   → ST_PlayerUpperState의 Condition·Task
```

- 공격 Pressed는 C++에서 소비한 뒤 이벤트로 전달. STT에서 같은 Pressed를 다시 소비하는 구조가 아님
- AttackCompleted는 Held 해제. C++이 RequestWeaponFireCompleted로 전달
- ProcessBufferedWeaponInputs는 Upper 명령 발신 전에 실제 Held를 WeaponComponent.SetFireInputHeld로 전달. 입력 소비·Tick 추가 없이 기존 C++ 처리 구간 사용
- Task의 AActor·APawn·AEntityCharacter는 Actor 바인딩. EntityContext는 Actor.PlayerContext 바인딩
- 자동 Reload Condition은 APlayerCharacter·APlayerContext 바인딩. 다른 무기 Condition의 EntityContext 바인딩과 변수명이 다름
- 현재 무기 참조는 Context.WeaponComp. 개별 WeaponInstance를 Condition에 별도 캐싱한 연결 없음
- 이번 변경에서 ProcessBufferedWeaponInputs를 RequestWeaponFire 호출로 교체하지 않음

## 3. Upper StateTree 구조

충전식 추가 연결은 아래 입력 기준 적용. 기존 SingleShot/RapidFire 전이 구조 유지

### 충전 입력과 발사 판정 — 2026-10-24

- 무기 DA ShootType=ChargedShot, AutoFireWhenFullyCharged=false. MinChargeRatio=0.2, PartialChargeDamageMultiplier=1, FullChargeDamageMultiplier=1.5
- 기존 ProcessBufferedWeaponInputs가 실제 Held를 전달하고, 해제 시 RequestWeaponFireCompleted 호출. 별도 Blueprint Tick/충전 시간 계산 없음
- 입력 해제를 CancelFireWeapon에 연결하지 않음. 입력 해제는 부분/완충 발사 요청이며 외부 취소·사망·교체만 기존 취소 경로
- Attack GA/Task는 IsFireInProgress가 충전을 포함한다는 기존 계약 사용. 입력 해제 직후 GA를 먼저 종료하면 발사 몽타주가 취소될 수 있으므로 OnWeaponFireFinished까지 기존 완료 대기 유지
- 최대 충전 시간에서 충전량 100% 유지, 버튼을 놓을 때 발사. 보스용 DA의 AutoFire=true와 구분
- 입력을 놓은 때의 배율 고정, 실제 목표점·머즐·공격 전달은 Notify에서 확정. 완충 전 해제 후 몽타주 대기 중 완충으로 승급 없음
- Draw가 끝나기 전에 이미 입력을 놓은 경우 해제형 충전의 지연 시작 거부
- ChargeVisualType=None/GrowingProjectile/WeaponEffect는 공격 규칙과 별개. 설정·정상/실패/취소 전체 경로는 [충전 연결](NPC%20연결·검증.md#충전-유탄착탄-경고-연결--2026-10-24) 참조
- 이번 변경의 빌드·UHT·Editor·Automation·PIE 미수행. 실제 GA 조기 종료 여부와 플레이어 입력 회귀는 사용자 확인 대상

```text
Root
└─ UpperState
   ├─ Holstered — STT_WeaponHolstered
   ├─ Holstering — STT_WeaponHolstering
   ├─ Ready — STT_WeaponReady
   ├─ Attack — STT_Attack
   ├─ Reload — STT_WeaponReload
   └─ Aim — STT_WeaponAim
      ├─ Aim Ready
      └─ Aim Attack — STT_Attack
```

현재 트리에 별도 Drawing 상태 없음. STT_Attack은 수납 상태로 진입하면 ExecuteDrawWeapon을 실행하고 Carry Ready를 기다리는 구성. Root의 Draw 명령 + CanDrawWeapon 전이는 비활성 상태. RequestWeaponDraw가 발행하는 Draw 명령만으로 기존 경로를 전면 대체하면 수납 중 발사가 끊길 수 있는 구조

| 출발 | 목적지 | 트리거·조건 |
|---|---|---|
| Root | UpperState | Draw + CanDrawWeapon. 비활성 |
| UpperState | Holstered | ForceHolster. Medium 우선순위 |
| UpperState | Holstering | Holster |
| UpperState | Reload | On Event + AutoReload + ShouldAutoReload. 신규 공통 전이 |
| Holstered | Reload | Reload + CanReload. 동일 형태 전이 하나만 유지 |
| Holstered | Aim | AimStarted + CanAim |
| Holstered | Attack | AttackStarted + CanAttack |
| Holstering | Holstered | On State Completed |
| Ready | Reload | Reload + CanReload |
| Ready | Aim | AimStarted + CanAim. 이벤트 선택 시 소비 false |
| Ready | Attack | AttackStarted + CanAttack |
| Attack | Ready | On State Completed |
| Reload | Ready | On State Completed |
| Aim | Reload | Reload + CanReload |
| Aim | Ready | 현재 비교값 AimStarted. 기존 토글 경로 유지 |
| Aim Ready | Aim Attack | AttackStarted + CanAttack |
| Aim Attack | Aim Ready | On State Completed |

자동 Reload Condition의 실제 구현은 ShouldAutoReload 반환. 2026-10-20 변경 후 현재 무기에 남아 있는 자동 요청과 실행 가능 여부만 조회. 빈 탄창 상태만으로 요청 생성 없음. Ready·Holstered의 On Tick 자동 전이 및 AttackStarted + 자동 Reload 전이 제거

## 4. Base StateTree와 상체의 연동

```text
Root
├─ GroundState
│  ├─ Idle
│  ├─ Walk
│  ├─ Sprint
│  ├─ JumpStart
│  ├─ Evading
│  └─ CancelSprint
├─ AirborneState
│  ├─ Falling
│  ├─ Jumping
│  └─ HangingDrop
└─ HangingState
   ├─ Hanging
   ├─ Vaulting
   └─ Mantle
```

- GroundState → Falling: CanFalling AND 공중 판정
- Idle → Walk·JumpStart·Evading: 해당 Condition의 On Tick
- Walk → Sprint: ToggleSprint 명령 AND CanSprint. Walk → Idle·JumpStart·Evading은 On Tick
- Sprint → Evading·JumpStart·Idle: On Tick. 완료 시 CanWalk이면 Walk
- Sprint → CancelSprint: CancelSprint OR ToggleSprint 명령
- JumpStart 완료 → Jumping. Jumping → Falling: CanFalling
- Evading 완료 → JumpStart·Sprint·Walk·Idle 순서의 조건 전이
- CancelSprint → Walk: LocomotionCommand 이벤트 + CharacterMovement.Velocity.X > 0 OR Velocity.Y > 0
- CancelSprint → Idle: 과거 `Event.Command.Locomotion.CancelSprint` 이벤트 + Velocity.X <= 0 AND Velocity.Y <= 0. 현재 로그의 Invalid GameplayTag 경고와 대조할 별도 항목. 이번 연사 수정에서 자동 변경 없음
- AirborneState → Hanging: CanHanging
- Falling → Sprint: CanSprint. Falling·HangingDrop → Idle: 지상 판정
- Hanging → HangingDrop: CheckHangingDrop. Hanging → Vaulting은 비활성. Hanging → Mantle은 CanMantle
- Vaulting 완료 → Falling. Mantle 완료 → Idle
- Upper의 ReadyEntered·FireEntered·AimEntered·ReloadEntered → EventBus → Mediator → Base CancelSprint 명령
- Base의 SprintEntered·EvadeEntered·TraversalEntered → EventBus → Mediator → Upper ForceHolster 명령

전이 이름만 보고 Sprint·Draw·Attack을 새 C++ 경로로 우회하지 않음. 기존 EventBus·Mediator 연결 유지

## 5. 확인한 문제와 C++ 변경

### 연사 간격

- 이전 C++: RapidFire도 한 발 몽타주가 끝날 때까지 bFireInProgress 유지. CanAttackWeapon이 다음 발사 차단
- Rifle Fire Montage 약 0.533초가 0.1초 쿨다운보다 긴 대기 원인. 실제 플레이어 간격은 수정 후 로그로 확인 필요
- 현재 C++: 실제 발사 확정 후 쿨다운 만료 시, 한 발 요청 방식 RapidFire의 남은 몽타주 정지 후 Sequence 성공 종료
- 2026-10-24 후속: 몽타주 정지는 에셋의 BlendOut 시간 사용. 0초 강제 정지로 포즈가 끊기는 요인 보정, Sequence 완료·다음 요청 허용 시점은 기존 쿨다운 기준 유지. 최신 변경의 빌드·PIE 미수행
- 정지 전에 Notify 구독과 해당 몽타주의 End Delegate 해제. 이전 종료 콜백이 다음 발사를 종료하는 현상 방지
- 탄 생성은 계속 Weapon_FireCommit에서 한 번. 쿨다운 시작도 실제 발사 시점. 몽타주 정지 자체에서 추가 탄 생성 없음
- 다음 발사는 기존 Triggered → StateTree → GA 경로. 상태 전이와 Notify까지의 프레임 시간이 추가되므로 정확히 0.100초 간격을 보장하는 구조는 아님
- SingleShot·지속 Beam의 기존 완료·Tick 경로 유지

### 연사 중 표시 세기 유지·수동 조준 반동 — 2026-10-25 갱신

- 원인: HandleAttackSequenceFinished의 BeginRecoilRecovery가 짧아진 한 발 완료마다 실행. 연사 도중 회복이 끼어드는 구조
- WeaponComponent.bFireInputHeld는 소유 Entity의 실제 입력 유지 상태. RapidFire 한 발만 실행하기 위해 즉시 false로 바꾸는 AttackSequenceHandler 내부 상태와 구분
- 성공한 RapidFire 한 발 완료 시 실제 Held=true이고 다음 발의 탄약이 남으면 반동 회복 보류. 실제 성공한 각 Commit의 반동 누적은 기존대로 실행
- 실제 입력 해제 후 실행 정리·발사 취소·탄약 소진이면 기존 RecoilRecoveryDuration으로 HUD 세기만 회복. 실제 조준은 자동 복귀하지 않음
- 매 Tick 전달되는 RequestWeaponFireCompleted가 진행 중 회복의 시작값·경과시간을 재설정하지 않도록 BeginRecoilRecovery 멱등 처리
- 새 발의 실제 Commit은 기존 AccumulateRecoil에서 회복 중단 후 잔여 반동에 추가 누적
- 최신 사용자 선택으로 실제 반동은 한 발의 FWeaponRecoilImpulse→ControlRotation 경로로 변경. 최종 카메라 Offset 전달 제거. 한 발 크기와 기존 DA 수치는 유지, 새 RecoilKickDuration 기본 0.05초는 초기 튜닝값
- PlayerCharacter의 Native 구독이 OnWeaponRecoilImpulse를 처리하므로 새 BP 바인딩 불필요. 기존 BP에 SetWeaponRecoilOffset 노드가 있으면 제거 대상, 함수는 구형 참조 로딩용 Deprecated/실행 효과 없음
- RecoilPitchAccumulationLimit=15·Yaw=8은 표시 세기 한도이며 실제 조준 상승 상한 아님. 15발 이후에도 새 발의 반동 유지, 마우스 하향 보정과 사격 종료 후 조준 유지 확인
- 무기 교체·빙의 전환은 아직 적용하지 않은 구간만 취소. 이미 적용한 조준은 원래 각도로 강제 복귀하지 않음
- 추가 Blueprint 연결 없음. GA_Attack의 정상 OnEnd에서 CancelFireWeapon을 호출하지 않는 기존 6절 기준 유지
- astra.Debug Weapon.Recoil 1에서 WeaponRecoil의 Shot·RecoveryBegin·RecoveryEnd, Held·IntensityPitch/Yaw·IntensityRecovering·ImpulsePitch/Yaw·KickDuration 확인. 기존 NPC.Combat 호환 유지
- 이번 변경 빌드·UHT·Editor·Automation·PIE 미수행. [현재 구현·공개 사례](../03_시스템%20설계/무기%20조준·반동·명중률.md#반동과-이동-사격)

### 중복 요청과 자동 재장전

- 이전 FireEquippedWeapon: 진행 중 StartFire가 거부돼도 WeaponActionState를 Idle로 덮어쓸 수 있는 구조
- 현재: 진행 중 Fire·지속 공격·쿨다운·Idle 이외 Action이면 상태 변경 전에 반환
- 자기 GA의 State.Combat.Attacking 태그로 자신을 차단하는 CanAttackWeapon 재호출은 추가하지 않음
- 이전 ShouldAutoReload·ShouldReloadOnFireRequest: 내부 ReloadHandler만 검사. 외부 WeaponComponent의 IsFireInProgress·지속 공격·Action 조건과 불일치
- 현재: 두 함수 모두 CanReloadWeapon Facade 사용. 자동 전이와 ExecuteReloadWeapon의 실행 전제 통일
- 2026-10-20: ShouldAutoReload는 사건에서 생성한 자동 요청도 필수 검사. 요청 대상 WeaponInstance·Sprint 상태·탄창 정책 검사 추가. 수동 CanReloadWeapon은 Sprint 취소 후 재장전을 허용하는 기존 정책 유지
- 예비 탄약·호환 탄종·Capability·차단 태그 검사는 기존 ReloadHandler 유지

### 2026-10-20 자동 재장전 요청과 Sprint 우선순위

사용자 재현: 빈 탄창·예비 탄약 확보 후 Reload 중 Sprint 입력 → Holstered·CancelSprint 반복. 자동 요청의 재생성과 SprintEntered의 ForceHolster가 맞물리는 경로

확정 정책: Sprint 실행 시 재장전 즉시 취소 및 기존 자동 요청 폐기. Sprint 종료만으로 취소된 재장전 재개 없음

| 사건 | WeaponComponent 처리 |
|---|---|
| 활성 무기 획득·교체 완료 | BindWeaponInstance 끝에서 빈 탄창이면 RequestAutoReload |
| 장전 탄수 양수 → 0 | HandleEquippedWeaponAmmoChanged에서 요청 생성 |
| 현재 무기와 호환되는 탄약 획득 성공 | Inventory.OnInventoryAmmunitionAcquired → RequestAutoReload(false) |
| 발사·쿨다운·꺼내기 종료 또는 Upper Ready | 기존 요청의 TryStartPendingAutoReload 호출 |
| Sprint·Evade·Traversal 진입 | 미실행 자동 요청 폐기 후 기존 ForceHolster |
| 교체·해제·재장전 취소·사망 | 이전 요청 폐기 |

탄약 획득은 빈 탄창뿐 아니라 덜 찬 탄창도 보충 요청. 가득 찬 탄창·호환되지 않는 탄약·획득 실패는 요청 없음. Inventory의 예약·소비 수량 변경은 획득 알림과 구분. 같은 자동 요청은 한 번만 발행. 실행 시도·ReloadEntered에서 소비, 실패·취소 후 자동 재시도 없음

현재 발사 중인 요청은 기존 발사 종료·쿨다운 종료·Ready 사건에서 실행 여부 확인. Tick·재시도 Timer 추가 없음. Sprint 중 발생한 자동 요청은 보관하지 않음

#### Upper 연결

1. Ready·Holstered의 On Tick → Reload 전이 제거
2. Ready·Holstered·Aim의 AttackStarted + 자동 Reload Condition → Reload 전이 제거. 일반 Attack 전이 유지
3. Holstered의 중복 수동 Reload 전이 하나 제거. Ready·Holstered·Aim의 수동 Reload + CanReload 전이 유지
4. UpperState 부모에 On Event 전이 추가: Tag=StateTree.Event.UpperCommand, Payload=FUpperStateCommandPayload, Command=AutoReload AND 기존 자동 Condition(ShouldAutoReload) → Reload
5. 새 Compare Enum의 Left를 해당 전이 이벤트 Payload.Command에 바인딩. 자동 Condition의 APlayerContext 등 기존 바인딩 유지
6. 부모 ForceHolster 전이 우선순위를 High로 지정. 자동 요청은 SprintEntered에서 먼저 폐기하므로 남은 AutoReload 이벤트의 Condition 결과 false
7. GA_WeaponReload와 STT_WeaponReload는 기존 실행 경로 재사용. 별도 자동 재장전 GA·Task 생성 없음
8. NPC Upper에도 같은 자동 명령을 사용할 경우 EntityContext에서 WeaponComp.ShouldAutoReload를 반환하는 BP Condition 사용. PlayerContext 전용 Condition의 NPC 재사용 금지

ReloadHandler의 종료 Delegate에 실행 세대 번호 추가. 취소 시 세대 무효화로 이전 몽타주의 늦은 종료 콜백이 같은 에셋으로 시작한 새 재장전을 종료하는 경로 차단

```text
장착·탄 소진·호환 탄약 획득
→ 현재 WeaponInstance에 자동 요청 생성
   ├─ 실행 전제 미충족 → 발사 종료·쿨다운 종료·Ready 사건에서 재확인
   └─ 실행 가능 → AutoReload 명령 한 번 발행
      → UpperState의 AutoReload AND ShouldAutoReload 전이
      → Reload Enter → 요청 소비 → 기존 GA 실행
         ├─ 정상 몽타주 종료 → 탄약 확정 → Ready
         └─ 실행 실패 → 실패 종료 → Ready, 같은 요청 자동 반복 없음

SprintEntered
→ 미실행 자동 요청 폐기 → ForceHolster
→ Reload Exit → GA 취소·CancelReloadWeapon
→ 탄약 미반영 → Sprint 유지
→ 기존 AutoReload 이벤트가 남아 있어도 요청 검사 실패

교체·해제·사망 → 이전 요청 폐기
수동 Reload → 기존 CanReload 조건·이벤트 → 동일 Reload Task
```

검증: 빈 무기 최초 획득·교체, 마지막 탄 자동 발사, 빈 탄창·부분 탄창의 호환 탄약 획득, 비호환 탄약 획득, 재장전 중 Sprint·Sprint 종료·새 수동 Reload, 재장전 취소 직후 동일 몽타주 재실행. C++ 정적 확인과 에셋 연결·PIE 결과 구분

## 6. Blueprint 연결 기준과 당시 진단

10/21 재장전 사용자 완료 확인. 아래 Reload 노드 ID·문제 경로는 10/20 진단과 수정 기준 기록이며 재적용 요구 아님. GA_Attack·공격 Task의 최신 적용 여부는 연사·반동 별도 잔여에서 확인

GA_Attack의 Activation Owned Tags에 State.Combat.Attacking, GA_WeaponReload에는 State.Combat.Reloading 설정 확인. 아래 Task는 해당 GA의 활성 수명에 맞춰 태그를 읽는 구성

### GA_WeaponReload — 실패 후 종료

제공된 그래프의 성공 경로는 OnWeaponReloadFinished 대기 방식. 성공 직후 EndAbility를 호출하는 구조가 아님

문제 경로: ExecuteReloadWeapon=false → Unbind → Condition 미연결·기본 true인 Branch → true 실행 핀 미연결. CancelAbility는 false 핀에만 연결되어 실행 실패 후 GA가 종료되지 않는 구조

정확한 연결:

1. `K2Node_IfThenElse_2`: Condition은 ExecuteReloadWeapon.ReturnValue 유지
2. false → `K2Node_RemoveDelegate_1` 유지
3. `K2Node_RemoveDelegate_1.then` → `K2Node_CallFunction_6.execute`의 CancelAbility로 직접 연결
4. 중간 `K2Node_IfThenElse_3` 제거. 실패 경로에 상수 true Branch를 두지 않음
5. 성공 경로의 완료 Event 바인딩·성공/실패 분기와 OnEnd의 자기 Event 해제·CancelReloadWeapon 유지

### GA_Attack — 시작 성공과 실제 완료 분리

10/20 제공 그래프: CommitAbility → FireEquippedWeapon → true이면 즉시 EndAbility. Assign OnWeaponFireFinished의 실행 핀 미연결·CommitAbility 반환값 미검사. 아래는 완료 수명 연결 기준

연결 변경:

1. Context·WeaponComp 유효성 확인 후 `Bind Event to On Weapon Fire Finished`
2. Target = GetEntityContext.WeaponComp. Event = 새 Custom Event `HandleFireFinished(bSucceeded: bool)`
3. Bind 완료 → CommitAbility → Branch(ReturnValue). false는 CancelAbility
4. true → FireEquippedWeapon → Branch(ReturnValue). false는 CancelAbility, true는 실행 대기
5. FireEquippedWeapon의 true 핀에서 즉시 EndAbility 호출 제거
6. HandleFireFinished → Branch(bSucceeded). true는 EndAbility, false는 CancelAbility
7. OnEndAbility → 같은 WeaponComp의 같은 Event만 Unbind. bWasCancelled=true이면 CancelFireWeapon 실행
8. 기존 무관한 구독을 지우는 Unbind All 사용 금지. 기존 미연결 Assign 노드 대신 자기 Event의 Bind/Unbind 사용

### STT_Attack — 한 번 활성화하고 완료 대기

현재: Enter에서 필요 시 ExecuteDrawWeapon·FireEntered 게시. Carry Ready인 모든 Tick에서 TryActivateAbilityByTag 실행. 활성화 반환값 미검사. Attacking 태그가 없으면 FinishTask(true)

bool `bAbilityStarted`, 기본 false 추가. 아래 대상은 모두 StateTree에 바인딩된 동일 EntityContext

- Enter: bAbilityStarted=false → StateTree에 바인딩된 Context·WeaponComp·StateEventBus·StateMediator·AbilitySystem·AEntityCharacter 사용
- 필수 참조 누락: 오류를 직접 확인하고 바인딩·초기화 원인 수정. IsValid 분기로 실행 생략·구성 오류 은폐 없음
- PublishUpperState(FireEntered, Source=AEntityCharacter) → Carry 검사
- Carry Ready: 아래 ActivateOnce 실행
- 그 외: ExecuteDrawWeapon → 성공이면 Draw 완료 대기, 실패면 FinishTask(false)
- ActivateOnce: TryActivateAbilityByTag(Ability.Weapon.Fire) → 반환 true이면 bAbilityStarted=true, false이면 FinishTask(false)
- Tick, bAbilityStarted=false: IsDrawInProgress이면 대기. Draw 종료 후 Carry Ready이면 ActivateOnce, 아니면 FinishTask(false)
- Tick, bAbilityStarted=true: Attacking 태그가 있으면 대기. 없으면 bAbilityStarted=false → FinishTask(DidLastFireSucceed)
- Exit: 진행 중 Draw 취소. bAbilityStarted=true인 경우 먼저 false 설정 후 CancelAbilityByTag(Ability.Weapon.Fire)
- 매 Tick 재활성화 노드 제거. 기존 Attack 완료 → Ready, Aim Attack 완료 → Aim Ready 전이 유지

### Condition·Reload Task

- STC_CanAttack: Branch와 true 전용 Return 대신 CanAttackWeapon.ReturnValue를 함수 ReturnValue에 직접 연결. true·false 결과 명확화
- STC_CanReload: 현재 CanReloadWeapon.ReturnValue 반환 유지
- 자동 Reload Condition: 현재 ShouldAutoReload 반환 유지. 공격 입력 필터를 임의 추가하지 않음
- STT_WeaponReload: 현재 Enter의 손 부착 정책 유지. EnterReadyCarryState를 실행하는 경로는 반환 false이면 FinishTask(false)
- PublishUpperState(ReloadEntered)의 Source=AEntityCharacter 연결
- GA 활성화가 false이면 FinishTask(false). 성공이면 Tick에서 Reloading 태그 종료 대기
- 태그 종료 시 FinishTask의 Succeeded=DidLastReloadSucceed. 현재 상수 true 대신 실제 결과 사용
- 정상·실패 모두 기존 On State Completed → Ready 전이 유지. Exit의 CancelReloadWeapon은 멱등 실행
- 제공된 Reload Enter 첫 Branch의 비교 노드 본문은 복사 텍스트에 미포함. 해당 조건을 상수 true로 단정하거나 임의 변경하지 않음

## 7. 정상·실패·취소 전체 실행 순서

```text
공격 Triggered → 입력 버퍼 → C++ 소비 → Upper AttackStarted
├─ 빈 탄창 + 실제 Reload 가능 → Reload
│  → STT_WeaponReload 손 부착·ReloadEntered → GA 활성화
│  → GA_WeaponReload: 완료 Event Bind → ExecuteReloadWeapon
│     ├─ false → 자기 Event Unbind → CancelAbility → Task 실패 → Ready
│     └─ true → Reload Montage 완료 대기
│        ├─ 정상 완료 → 탄약 확정 → OnWeaponReloadFinished(true)
│        │  → 자기 Event Unbind → EndAbility → Task 성공 → Ready
│        └─ 중단/실패 → 탄약 확정 없음 → Event(false)·GA 취소 → Ready
├─ 빈 탄창 + 예비탄/Capability 등 불충족 → Reload 전이 없음, 발사 없음
└─ 발사 가능 → Attack 또는 Aim Attack
   → STT_Attack Enter: FireEntered → 필요 시 Draw 대기
   → GA 한 번 활성화
   → GA_Attack: 완료 Event Bind → CommitAbility → FireEquippedWeapon
      ├─ Commit/실행 실패 → 자기 Event 해제·CancelAbility → Task 종료
      └─ 실행 성공 → GA·Task 유지
         → Fire Montage → Weapon_FireCommit → 탄 생성·탄약 소비
         → RapidFire 쿨다운 만료 → 이전 Notify/End 구독 해제·몽타주 정지
         → Sequence 성공 → OnWeaponFireFinished → GA End
         → Task 완료 → Ready 또는 Aim Ready → 다음 Triggered 처리

외부 취소: State Exit → GA 취소 → 자기 Event 해제 → Fire/Draw/Reload 정리
이미 발사한 탄의 쿨다운은 취소로 환불하지 않음
재장전 탄약은 정상 Montage 종료에서만 확정
```

## 8. 사용자 검증

1. 사용자 C++ 빌드 후 위 Blueprint 연결·관련 StateTree Compile
2. `astra.NPC.CombatDebug 1` 활성화. Player WeaponShot을 NPC와 Owner별 분리
3. 라이플 연사: 0.533초 몽타주 전체 대기 제거, Interval>=AttackCooldown 확인. 정확한 10발/초는 요구하지 않음
4. 한 번의 FireCommit에 한 발·한 번의 탄약 소비. 이전 몽타주의 종료 콜백이 다음 발사를 끝내지 않는지 확인
5. 버튼 해제 후 새 발사 요청 중지. 이미 시작된 한 발의 후반 동작 정리·쿨다운 유지
6. Ready·Holstered·Aim에서 빈 탄창 + 호환 예비 탄약 보유 시 Reload 진입·정상 종료 후 보충
7. Reload 실행 거부 시 Reloading 태그·GA 잔류 없음. Task가 실패로 Ready 복귀
8. 예비 탄약 없음·탄종 불일치·Reload Capability 없음은 재장전 미실행이 정상. 해당 조건을 실행 로그 없이 버그로 단정하지 않음
9. 발사 중 중복 요청이 기존 Action을 Idle로 바꾸지 않는지, Reload가 발사 진행 중 먼저 진입하지 않는지 확인
10. Sprint·Evade·Traversal·피격·사망 취소, 권총·지속 Beam·무기 교체 회귀 확인
11. 탄약이 남은 상태의 라이플 연사: 매 Shot의 조준 Impulse 1회·표시 세기 누적 유지, 한 발마다 표시 RecoveryBegin·0 복귀가 반복되지 않는지 확인. 15발 이후 반동 유지·마우스 하향 보정·캐릭터 구도 확인
12. 실제 버튼 해제·취소·탄창 소진: 실제 조준 방향 유지, 표시 세기만 RecoveryDuration에 따라 회복. 0이면 표시만 즉시 회복. 무기 교체·빙의 전환·30/60/120fps·Pitch 제한·벽 근처 스프링암 확인

NPC 사선의 실제 Hit Actor·자기 발사체 가설은 NPC 연결·검증 문서에서 추적. 플레이어 연사 원인과 동일하게 확정하지 않음
