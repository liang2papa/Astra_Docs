# 99_작업 규칙

```text
요청·변경 범위 확인 → 변경안·영향 설명 → 사용자 승인
→ C++ 수정 → 전체 빌드 → 사용자 Editor 연결 → PIE·로그 검증 → 문서 갱신

사용자가 직접 빌드 지정 / 권한 문제 → 사용자 빌드
Blueprint 안내 → 정상·실패·취소 경로 전체 도식화
```

## 설계 의도

텍스트로 검토할 C++ 작업과 사용자가 확인할 Editor 콘텐츠 작업 분리

Blueprint 안내의 정상·실패·취소 경로 재현 가능성 확보

## 1. 최우선 원칙

1. Unreal Engine 5.8 규칙이 Unity 레거시 규칙보다 우선
2. 동일한 정책 계산을 Blueprint와 C++에 중복 구현하지 않음. 전이 사전 검사와 실행 시점 재검사는 별도 책임
3. 수치 하드코딩을 피하고 DataAsset 또는 명명된 멤버 변수로 노출
4. 게임플레이 사실은 단일 소유자만 변경
5. Context에는 참조만 넣고 판단·전이·실행 로직을 넣지 않음
6. Mediator는 이벤트와 정책을 라우팅하며 벡터 계산이나 세부 도메인 로직을 직접 구현하지 않음

## 2. Blueprint와 C++ 경계

### Blueprint 우선

- StateTree와 Condition/Task의 프로젝트별 구성
- Gameplay Ability 구체 클래스
- Animation Blueprint, Montage, Notify, Aim Offset, BlendSpace
- DataAsset 값과 콘텐츠 에셋 연결
- 반복 튜닝이 필요한 카메라·애니메이션 수치

### C++ 우선

- 공통 생명주기와 초기화 안전장치
- 반복되는 엔진 API 래퍼
- 상태 간 공통 정책과 이벤트 기반 인프라
- 계산량이 크거나 네이티브 API 접근이 중요한 로직
- 실패 복구, Delegate 해제, Timer 정리

### 예외

Blueprint 생성 우선

필수 컴포넌트 누락으로 실행이 불가능하거나 모든 파생 Blueprint가 필요한 경우: C++ 기본 서브오브젝트 허용

예외 적용 이유는 문서에 기록

## 3. 계층과 통신

- 객체 정체성은 [Entity / Item / Prop](../02_%EA%B2%8C%EC%9E%84%20%EA%B8%B0%ED%9A%8D/%EA%B2%8C%EC%9E%84%20%EA%B0%9D%EC%B2%B4%20%EB%B6%84%EB%A5%98.md)으로 구분
- Interactable, Damageable, Shop, Container 같은 기능은 최상위 분류가 아니라 Capability로 조합
- 하위 컴포넌트끼리 직접 참조해 정책을 결정하지 않음
- StateTree Task는 EventBus에 상태 진입 사실을 게시
- EntityStateMediator가 이를 구독해 다른 StateTree에 명령을 보냄
- Damage/Death처럼 외부에서 발생한 사실은 HealthComponent 이벤트를 Mediator가 받아 상태 명령으로 변환
- UI는 Model/Component의 이벤트를 구독하며 상태를 직접 변경하지 않음

## 4. 데이터 소유권

목표 책임 기준. StatusModel에 남은 실제 구현과 단계적 이전 상태는 시스템 설계·이슈 가이드에서 구분

| 사실 | 유일한 변경 주체 |
|---|---|
| 체력·스태미나·영혼 에너지 | ASC / AttributeSet |
| Ability 비용·쿨다운 | GameplayEffect / ASC |
| 개별 무기의 등록 탄종·등록 탄수 | WeaponInstance |
| 탄약 Item Total·Reserved·Available | InventoryComponent |
| 장착 슬롯과 활성 WeaponInstance | GearComponent |
| 장착·손/홀스터 상태 | Upper StateTree Task + WeaponComponent |
| 로코모션 실행 상태 | Base StateTree |
| 파쿠르 이동 실행 | EntityLocomotionComponent |
| 애니메이션 표현 | AnimBP — 읽기 전용 |

## 5. StateTree 규칙

- Condition은 전이 가능 여부만 판단
- Task가 상태 진입·실행·종료와 GA 활성화 요청을 담당
- GA는 활성화 시점에 탄약·사망·기절·비용 재검사
- Condition: 전이 후보 검사 / GA: 실제 실행 권한 검사
- 전이 후 실행까지의 상태 변화에 대응하는 의도적인 이중 검사
- 이벤트 전이를 우선하고 반드시 필요한 경우만 On Tick 전이를 사용
- 성공과 실패 목적지가 다르면 전이를 분리
- 동일 목적지라면 `On State Completed` 하나를 사용
- ExitState는 중단·실패·사망 경로에서도 호출될 수 있다고 가정하고 복구 코드를 멱등하게 작성
- STC/STT의 공통 바인딩은 가능하면 `Actor + EntityContext`로 단순화
- StateTree 간 직접 참조 금지. EntityStateMediator / EventBus 사용

```text
Condition 사전 검사
├─ 실패 → 전이하지 않음
└─ 통과 → Task 진입 → EventBus에 진입 사실 게시
   → Mediator를 통한 GA 활성화 요청
   → GA의 탄약·사망·기절·비용 재검사
   ├─ 실패 → 활성화 거부·종료 → Task 실패 처리
   └─ 통과 → Domain Component 실행 → 성공·실패 결과 처리
취소 → 실행 종료 → Task / Domain의 복구·자원 정리
```

## 6. Animation 규칙

- Animation Blueprint는 StateTree를 직접 제어하지 않음
- Montage Notify는 시각 프레임과 게임플레이 사건의 동기화 지점으로 사용
- Notify가 누락되거나 Montage가 중단되는 경우 Domain Component에 안전한 대체 경로를 둠
- Root Motion으로 환경 목표점에 정확히 맞춰야 하는 동작은 Motion Warping을 사용
- 캡슐의 위치와 메시의 시각 오차를 분리해서 진단
- 손·무릎 접촉 오차는 애니메이션, Control Rig, IK로 보정하고 캡슐 위치를 임의로 흔들지 않음

## 7. 파쿠르 복구 규칙

Hanging, Mantle, Vault, Evade가 성공·실패·중단될 때 다음을 명시적으로 복구

- MovementMode
- GravityScale
- Velocity
- LedgeGrabbed 상태
- 재감지 쿨다운
- 충돌 설정과 임시 Ignore
- 실행 중인 Timeline/Timer/Montage

Hanging 중 0으로 변경한 GravityScale을 정상 기본값으로 저장 금지

정상 값은 초기화 시점에 별도 캐싱

## 8. 무기·전투 규칙

- 조준·발사·재장전 StateTree와 GA는 무기를 사용하는 Entity 행동으로 분류
- Weapon Item은 WeaponDataAsset, WeaponInstance, WeaponComponent를 통해 정적 정의·인스턴스 상태·실행 결과를 소유
- 무기별 차이는 WeaponDataAsset에 둠
- WeaponDataAsset: Mesh·Socket·피해·사거리·반동·Montage 정적 정의
- WeaponInstance: 등록 탄종·등록 탄수와 개별 강화·내구도·부착물 상태
- GearComponent: 장착 슬롯·활성 WeaponInstance 관리
- InventoryComponent: Ammunition Item·탄약 Reservation 소유
- WeaponComponent: 활성 WeaponInstance 참조, 장착·수납·발사·재장전 조율
- 발사체 방향은 카메라 Ray의 목표점과 Muzzle 위치를 이용해 계산
- 카메라 Ray는 소유 캐릭터와 장착 무기를 무시
- Muzzle Socket의 로컬 축만 신뢰하지 말고 목표점을 향하는 회전을 계산
- 플레이어 명중 규칙: [무기 조준·반동·명중률](../02_%EA%B2%8C%EC%9E%84%20%EA%B8%B0%ED%9A%8D/%EC%8B%9C%EC%8A%A4%ED%85%9C%20%EA%B8%B0%ED%9A%8D/%EB%AC%B4%EA%B8%B0%20%EC%A1%B0%EC%A4%80%C2%B7%EB%B0%98%EB%8F%99%C2%B7%EB%AA%85%EC%A4%91%EB%A5%A0.md)
- NPC 정확도는 NPC 성향과 이동 패널티로 계산

## 9. 코드 변경 절차

1. 변경 코드 전문 또는 정확한 변경안을 먼저 제시, 제시하기 전 조건을 파악하고 반드시 사용자에게 우선적으로 질문
2. 영향 범위와 대안 논의
3. 사용자 승인
4. C++ 반영
5. Editor와 Visual Studio를 닫고 전체 Development Editor 빌드
6. 사용자가 Blueprint/DataAsset/Animation 에셋 연결
7. 플레이 테스트 및 로그 확인
8. Wiki와 일일 리포트 갱신


사용자가 `바로 반영`, `승인 없이 진행`을 명시하면 1~3단계 생략 가능

사용자 직접 빌드 지정 시 코드 반영과 검증 안내까지 수행

### 헤더 정리 기준

- 공개·내부 메서드에는 책임을 알 수 있는 한 줄 설명을 둠
- Blueprint 노출 카테고리는 기능별 계층으로 통일
- WeaponComponent는 `Weapon | State`, `Weapon | Attack`, `Weapon | Recoil`, `Weapon | Accuracy`, `Weapon | Events`처럼 도메인 기준으로 구분
- PlayerCharacter는 `Player | Design Data`, `Player | Input`, `Player | Camera`, `Player | Components`, `Player | StateTree`, `Player | Events`, `Player | Runtime`으로 구분
- 비공개 C++ 메서드는 에디터 Category 대상이 아니므로 선언 위치와 주석으로 역할을 표시

## 10. 에디터 자동화 제한

- Blueprint·StateTree·Animation Blueprint·Montage·DataAsset 변경: 사용자 직접 수행
- Codex는 노드 이름, 핀 연결, 경로, 설정값과 전체 실행 순서를 제공
- Unreal Editor UI 자동화나 콘텐츠 바이너리 직접 변경은 사용자가 명시적으로 허용한 경우에만 수행
- 빌드 권한 문제 발생 시 사용자 직접 수행. Codex는 Target·검증 항목 제공
- 사용자 공유 첫 오류·로그를 기준으로 후속 수정
- Blueprint 설명 마지막에는 정상·실패·취소 분기를 포함한 전체 노드 실행 순서 도식화

## 11. 문서 규칙

- 기획: 정의·가능한 행동·게임 규칙
- 시스템 설계: Unreal 구현 방법
- 애니메이션 설계: 상태 표현·애셋·전이·보정
- 같은 대상의 문서명과 행동 항목 1:1 대응
- 기획 문서: 기획 의도
- 시스템·애니메이션 설계 문서: 설계 의도
- 의도 근거가 없으면 빈칸 유지
- 재사용 기술: 08_기술 위키_공통 가이드
- 일정 이슈: ID·상태·기술 상세 링크. 증상·원인·해결·검증은 기술 가이드
- 대화의 제안·과거 구현·현재 코드·사용자 완료 확인을 구분
- 커밋·푸시는 사용자 수행
- 본문: 단문형·명사형 종결
- 고유 명칭: 영혼 결속
- Markdown 최상위 제목 유지
- 일일 리포트의 요약 작성 시 PIE 필요와 같은 항목은 제외

- Markdown은 저장소에서 직접 검토 가능한 기본 형식
- Word/Excel 산출물을 만들 때는 본문 글꼴을 맑은 고딕으로 통일
- GitHub Markdown의 실제 표시 글꼴은 GitHub와 브라우저 설정을 따르므로 문서에서 강제하지 않음
- 기존 설명이 잘못되었으면 수정 이력만 남기고 잘못된 내용을 본문 규칙으로 유지하지 않음

## 12. 코드 작성 규칙

- UPROPERTY의 일반 지정자는 한 줄에 작성
- meta 내부도 항목별로 줄을 나누지 않고 한 줄로 작성
- 길이가 무리하지 않으면 meta까지 전부 한 줄로 작성
- 단순 변수 선언, 계산식, 함수 호출도 충분히 읽을 수 있으면 한 줄 유지
- 형식적인 이유로 짧은 코드를 여러 줄로 분할하지 않음
- 구체적인 최대 글자 수는 정하지 않았음
- 툴팁(주석) 작성의 경우 단문 형태로 작성하고, 마침표 없이 작성
    예시) 플레이어 공격용 함수
