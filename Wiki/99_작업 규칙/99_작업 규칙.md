## 설계 의도

텍스트로 검토할 C++ 작업과 사용자가 확인할 Editor 콘텐츠 작업 분리

Blueprint 안내의 정상·실패·취소 경로 재현 가능성 확보

## 1. 최우선 원칙

1. Unreal Engine 5.8 규칙이 Unity 레거시 규칙보다 우선
2. 동일한 정책 계산을 Blueprint와 C++에 중복 구현하지 않음. 전이 사전 검사와 실행 시점 재검사는 별도 책임
3. 수치 하드코딩을 피하고 DataAsset 또는 명명된 멤버 변수로 노출
4. 게임플레이 사실은 단일 소유자만 변경
5. Context에는 참조만 넣고 판단·전이·실행 로직을 넣지 않음
6. Mediator는 이벤트와 정책을 라우팅하며 벡터 계산이나 세부 도메인 로직을 직접 구현하지 않음
7. 기능 추가 전 기존 선언·구현·호출부·데이터 소유권을 확인하고 재사용/분기 확장을 우선 검토. 같은 책임의 Component·Handler·Subsystem·GA·데이터·타이머를 중복 생성하지 않음

## 2. Blueprint와 C++ 경계

### Blueprint 우선

- StateTree와 Condition/Task의 프로젝트별 구성
- Gameplay Ability 구체 클래스
- Animation Blueprint, Montage, Notify, Aim Offset, BlendSpace
- DataAsset 값과 콘텐츠 에셋 연결
- 반복 튜닝이 필요한 카메라·애니메이션 수치

### Blueprint 구조 문서 유지 — 2026-10-26 사용자 지정

- 사용자가 제공하거나 Editor에서 확인한 최신 Blueprint 구조는 해당 기능의 **시스템 설계 문서**에 기록. QA 문서에만 흩어 두지 않음
- 에셋 경로·상속 참조·사용 변수/타입/기본값·Context 바인딩·이벤트별 실행/데이터 핀 연결·태그/Delegate·정상/실패/취소 전체 흐름을 함께 기록
- 첨부/Editor 확인 날짜와 근거를 남기고, **현재 확인된 실제 연결**, **수정해야 할 연결**, **적용/Compile/PIE 확인 여부**를 구분. 수정안을 실제 적용된 구조로 기록하지 않음
- 다음 분석·수정은 이 설계 문서와 현재 C++ 호출 경로를 먼저 대조. 이미 기록한 구조를 사용자에게 반복해서 전체 복사·붙여넣기 요청하지 않음. 문서 이후 변경/실행 불일치로 추가 확인이 필요할 때만 해당 부분을 확인
- 구조가 갱신되면 기존 기준도 함께 갱신하고 이전 내용은 이력으로 표시. 관련 QA·현재 작업 상태에서는 설계 문서의 해당 절을 링크

### C++ 우선

- 공통 생명주기와 초기화 안전장치
- 반복되는 엔진 API 래퍼
- 상태 간 공통 정책과 이벤트 기반 인프라
- 계산량이 크거나 네이티브 API 접근이 중요한 로직
- 실패 복구, Delegate 해제, Timer 정리

Blueprint 생성 우선

## 3. 계층과 통신

- 객체 정체성은 [Entity / Item / Prop](../02_%EA%B2%8C%EC%9E%84%20%EA%B8%B0%ED%9A%8D/%EA%B2%8C%EC%9E%84%20%EA%B0%9D%EC%B2%B4%20%EB%B6%84%EB%A5%98.md)으로 구분
- Interactable, Damageable, Shop, Container 같은 기능은 최상위 분류가 아니라 Capability로 조합
- 하위 컴포넌트끼리 직접 참조해 정책을 결정하지 않음
- StateTree Task는 EventBus에 상태 진입 사실을 게시
- EntityStateMediator가 이를 구독해 다른 StateTree에 명령을 보냄
- Damage/Death처럼 외부에서 발생한 사실은 HealthComponent 이벤트를 Mediator가 받아 상태 명령으로 변환
- UI는 Model/Component의 이벤트를 구독하며 상태를 직접 변경하지 않음

### 객체 간 참조 일관성 — 2026-10-28

- Controller·Character·PlayerState는 역할/소유권이 다른 객체. 이름이나 조작 관계로 상위/하위 서열을 만들지 않음. Facade와 내부 Handler의 소유/위임 관계는 별도로 명시
- 직접 참조는 엔진 연결·초기화/해제·필요한 공통 조회·공개 실행 계약으로 한정. 참조 대상, 필요한 이유, 읽기/요청/변경 범위와 수명을 확인
- 하위 실행부에서 구체 Player/AIController를 찾아 판단·추격·Brain 상태를 변경하지 않음. 결과/요청은 기존 Facade/Delegate/명령 경계로 중계
- 소유자/조립부가 Context에 제공한 육체·Mesh·Movement 등 필요한 실행 참조는 허용. Context에 구체 조종자 포인터를 넣고 기존 역방향 호출을 옮기는 것으로 분리 완료 처리하지 않음
- public 접근·기반 클래스 Cast·약한 참조·헤더 순환 없음은 기능 정책 의존의 적합성을 보장하지 않음. 모든 조회를 Mediator에 집중하거나 포인터마다 인터페이스를 신설하지 않음
- 기존 구체 의존은 현행 구현과 정리 목표를 구분하여 [아키텍처 참조 계약·정리 범위](../03_시스템%20설계/시스템%20아키텍처.md#참조와-통신-계약--2026-10-28)에 기록. 신규 변경은 같은 경계 기준 적용

## 5. StateTree 규칙

- Condition은 전이 가능 여부만 판단
- Task가 상태 진입·실행·종료와 GA 활성화 요청을 담당
- GA는 활성화 시점에 탄약·사망·기절·비용 재검사
- GA 기반 행동의 실행 지시는 StateTree Task에서 시작. GA는 C++ 실행 요청·결과·취소·종료 처리, C++ 실행부는 실제 동작·완료 알림·자원 정리 담당
- 사망도 Health 사실 → Mediator 명령 → Base Death Task → GA → 공통 C++ 실행 순서 적용. Mediator의 사망 GA 직접 활성화·연출 우회 실행 금지
- Condition: 전이 후보 검사 / GA: 실제 실행 권한 검사
- 전이 후 실행까지의 상태 변화에 대응하는 의도적인 이중 검사
- 이벤트 전이를 우선하고 반드시 필요한 경우만 On Tick 전이를 사용
- 성공과 실패 목적지가 다르면 전이를 분리
- 동일 목적지라면 `On State Completed` 하나를 사용
- ExitState는 중단·실패·사망 경로에서도 호출될 수 있다고 가정하고 복구 코드를 멱등하게 작성
- STC/STT의 공통 바인딩은 가능하면 `Actor + EntityContext`로 단순화
- STT_EntityBase 자식 Task는 부모의 actor·character·entitycontext·pawn 바인딩 참조 사용. 자식에서 같은 참조를 다시 캐스팅·조회·저장하지 않음
- ExitState 작업은 실제로 정리할 책임이 있을 때만 추가. STT_EntityDeath는 ExitState 추가 작업 없음. GA·C++의 종료 정리 중복 금지
- StateTree 간 직접 참조 금지. EntityStateMediator / EventBus 사용
- 크로스 트리 상태 판별은 ASC 게임플레이 태그 기반. StateTree 상태의 Tag 속성은 StateTree 세부 식별용으로 ASC에 투영되지 않음

### STT와 C++ 컴포넌트 경계

- STT Blueprint는 "언제"만 담당 — 진입·이탈 오케스트레이션과 호출 순서 결정
- C++ 컴포넌트는 "무엇을/어떻게"를 소유 — 태그 조작, 몽타주 재생, 물리 이동과 복구
- Blueprint에 AddLooseGameplayTags, Montage Play 직접 노드 금지 — 에셋은 파라미터로 전달하고 실행은 C++ 경로
- 입력 소비는 전이 확정 후 진입 STT의 첫 실행에서 한 번. STC에서 소비 금지

### Tick 사용 규칙

- 매 프레임 갱신은 중재자(Mediator)와 StateTree Task만 수행
- 중재자가 자신이 소유한 하위 컴포넌트의 갱신 메서드를 호출하는 방식 — 하위 컴포넌트는 `PrimaryComponentTick`을 비활성화하고 갱신 메서드만 제공
- 하위 컴포넌트가 직접 틱을 수행하지 않음
- 틱 루프 본체는 C++에서 수행 — Blueprint는 바인딩·알림 수준에서만 사용
- 엔진 시스템이 자체 틱을 필요로 하는 컴포넌트는 예외 — StateTreeComponent, AbilitySystemComponent, TimelineComponent, CharacterMovementComponent 등
- 사용하지 않는 구간의 틱은 상태에 따라 On/Off (`SetComponentTickEnabled`)
- 갱신 순서가 결과에 영향을 주면 `AddTickPrerequisiteComponent`로 순서 고정

```text
Condition 사전 검사
├─ 실패 → 전이하지 않음
└─ 통과 → Task 진입 → EventBus에 진입 사실 게시
   → Mediator를 통한 GA 활성화 요청
   → GA의 탄약·사망·기절·비용 재검사
   ├─ 실패 → 활성화 거부·종료 → Task 실패 처리
   └─ 통과 → Domain Component 실행 → 성공·실패 결과 처리
취소 → 실행 종료 → Task / Domain의 복구·자원 정리
```

## 6. Animation 규칙

- Animation Blueprint는 StateTree를 직접 제어하지 않음
- 발사·재장전·Mantle·사망 몽타주는 현재 캐릭터 ABP 기본값 소유. 사망은 배열에서 시작 시 한 개 무작위 선택. Task·무기 DA·캐릭터 BP에 캐릭터별 몽타주 복제 없음. 실행부는 현재 AnimInstance 설정 조회 후 기존 게임플레이 수명·완료·복구 처리
- 무기 모델의 손·홀스터 상대 Transform은 현재 ABP의 WeaponDataAsset.ItemID별 설정 소유. 같은 WeaponType의 다른 모델 구분, SocketName·Mesh·무기 조준 보정 수치는 무기 DA 유지
- 인간형 AnimInstance 초기화는 EntityCharacter 공통 C++ 경로. 캐릭터 BP의 Cast·InitABPClass 초기화 체인 중복 없음
- Montage Notify는 시각 프레임과 게임플레이 사건의 동기화 지점으로 사용
- Notify가 누락되거나 Montage가 중단되는 경우 Domain Component에 안전한 대체 경로를 둠
- Root Motion으로 환경 목표점에 정확히 맞춰야 하는 동작은 Motion Warping을 사용
- 캡슐의 위치와 메시의 시각 오차를 분리해서 진단
- 손·무릎 접촉 오차는 애니메이션, Control Rig, IK로 보정하고 캡슐 위치를 임의로 흔들지 않음

## 7. 파쿠르 복구 규칙

Hanging, Mantle, Vault, Evade가 성공·실패·중단될 때 다음을 명시적으로 복구

- MovementMode
- GravityScale
- Velocity
- LedgeGrabbed 상태
- 재감지 쿨다운
- 충돌 설정과 임시 Ignore
- 실행 중인 Timeline/Timer/Montage

Hanging 중 0으로 변경한 GravityScale을 정상 기본값으로 저장 금지

정상 값은 초기화 시점에 별도 캐싱

## 8. 무기·전투 규칙

- 조준·발사·재장전 StateTree와 GA는 무기를 사용하는 Entity 행동으로 분류
- Weapon Item은 WeaponDataAsset, WeaponInstance, WeaponComponent를 통해 정적 정의·인스턴스 상태·실행 결과를 소유
- 무기별 차이는 WeaponDataAsset에 둠
- WeaponDataAsset: Mesh·Socket·피해·사거리·반동·총열 시각 조준 보정·Equip/Holster 정적 정의. 발사·재장전 몽타주는 캐릭터 ABP 설정. DryFire 몽타주·사운드는 미사용 항목 제거
- WeaponInstance: 등록 탄종·등록 탄수와 개별 강화·내구도·부착물 상태
- GearComponent: 장착 슬롯·활성 WeaponInstance 관리
- InventoryComponent: Ammunition Item·탄약 Reservation 소유
- WeaponComponent: 활성 WeaponInstance 참조, 장착·수납·발사·재장전 조율
- 발사체 방향은 카메라 Ray의 목표점과 Muzzle 위치를 이용해 계산
- 카메라 Ray는 소유 캐릭터와 장착 무기를 무시
- Muzzle Socket의 로컬 축만 신뢰하지 말고 목표점을 향하는 회전을 계산
- 플레이어 명중 규칙: [무기 조준·반동·명중률](../02_%EA%B2%8C%EC%9E%84%20%EA%B8%B0%ED%9A%8D/%EC%8B%9C%EC%8A%A4%ED%85%9C%20%EA%B8%B0%ED%9A%8D/%EB%AC%B4%EA%B8%B0%20%EC%A1%B0%EC%A4%80%C2%B7%EB%B0%98%EB%8F%99%C2%B7%EB%AA%85%EC%A4%91%EB%A5%A0.md)
- NPC 정확도는 NPC 성향과 이동 패널티로 계산

## 9. 코드 변경 절차

### 프로젝트 디버그 관리

- 2026-10-24 사용자 요청: 디버그는 `Utils/Debug/UAstraDebugSubsystem`으로 모음. 콘솔 등록·목록·현재 값·사용처·로그 포맷·화면 표시·출력 간격/중복 억제는 해당 서브시스템 소유
- 새 디버그는 중앙 등록부에 추가. 기능 cpp에 독립 콘솔 변수·문자열 FindConsoleVariable·직접 DrawDebug·진단 전용 타이머/중복 상태를 분산 추가하지 않음
- 기능 코드에는 진단 서비스 호출만 두고 실제 오류·실행 실패 경고·checkf는 원래 기능부 유지
- 전체 옵션은 `astra.Debug`에서 조회. 기존 직접 명령은 호환 유지. 상세 기준: [디버그 서브시스템](../03_시스템%20설계/디버그%20서브시스템.md)

### 구현 전 중복 점검 — 2026-10-26 사용자 지정

1. 새 클래스명부터 정하지 않고 요청 기능을 판단·실행·수명·데이터·연출 책임으로 구분
2. 관련 기존 타입의 선언·정의·실제 호출부와 초기화·정상/실패/취소·사망 정리를 대조. 이름이 다르거나 특정 경로에서 아직 호출하지 않는다는 이유만으로 기능이 없다고 판단하지 않음
3. 기존 Facade와 실행 Handler 내부 분기·공통 함수 확장으로 처리 가능한지 먼저 확인. 새 Handler 신설도 기존 Handler의 담당 범위로 수용할 수 없는 이유가 있을 때 검토
4. 몽타주·쿨다운·완료 사건·피해·자원·상태의 기존 단일 소유자 유지. 새 구현을 붙이기 위해 동일 수치·타이머·상태·Delegate 완료 경로를 복제하지 않음. 기존 DA→ASC 원본과 실행 시 읽은 스냅샷은 구분
5. 변경안에 기존 재사용 항목·실제 누락·수정할 호출 경로·새 타입 필요 근거 명시. 플레이어/NPC 공통 실행과 입력·AI 정책의 차이를 구분
6. 기존 구조로 충분하면 새 타입을 만들지 않음. 분리가 필요하면 중복이 아닌 고유 책임·연결/정리 경계·영향 범위 제시 후 합의된 범위로 구현

- 애니메이션 설계: 상태 표현·애셋·전이·보정
- 같은 대상의 문서명과 행동 항목 1:1 대응
- 기획 문서: 기획 의도
- 시스템·애니메이션 설계 문서: 설계 의도
- 의도 근거가 없으면 빈칸 유지
- 재사용 기술: 08_기술 위키_공통 가이드
- 일정 이슈: ID·상태·기술 상세 링크. 증상·원인·해결·검증은 기술 가이드
- 대화의 제안·과거 구현·현재 코드·사용자 완료 확인을 구분
- 커밋·푸시는 사용자 수행
- 본문: 단문형·명사형 종결
- 고유 명칭: 영혼 결속
- Markdown 최상위 제목 유지
- 일일 리포트의 요약 작성 시 PIE 필요와 같은 항목은 제외
- 일일 리포트의 귀속 날짜는 사용자 현지 시각 기준 해당 날짜 09:00부터 다음 날 08:00까지. 예: 10월 26일 새벽 작업은 10월 25일 리포트에 기록. 자정을 넘겼다는 이유로 다음 날짜 리포트를 새로 만들지 않음
- 잘못된 날짜에 작성한 리포트는 해당 작업일 리포트의 목표·완료·설계·검증·잔여·다음 작업에 내용을 보존해 통합하고 날짜별 목록 링크도 정리
- 일일 리포트에는 집계 시간을 기록하지 않음
- 일일 리포트 항목은 종결 어미 없이 명사형으로 작성
    예시) EntityStatusModel, PlayerStatusModel 소스 제거
    예시) Character/Pawn이 Entity ASC와 HP·이동·회피·스태미너 AttributeSet을 소유하도록 구조 변경
    부적합 예시) EntityStatusModel 소스를 제거함

- Markdown은 저장소에서 직접 검토 가능한 기본 형식
- Word/Excel 산출물을 만들 때는 본문 글꼴을 맑은 고딕으로 통일
- GitHub Markdown의 실제 표시 글꼴은 GitHub와 브라우저 설정을 따르므로 문서에서 강제하지 않음
- 기존 설명이 잘못되었으면 수정 이력만 남기고 잘못된 내용을 본문 규칙으로 유지하지 않음
- 같은 기능의 후속 증상·Editor 연결 안내는 기존 담당 문서에 통합. 별도 책임 없는 대화별 문서 생성 지양
- 현재 작업 상태에는 완료·잔여·다음 작업·담당 문서 링크만 기록. 구현·핀 연결·로그 상세 중복 없음
- 통합 전 고유 설정·실패/취소 경로·완료 확인 보존, 내부 링크 갱신 후 중복 문서 제거. 날짜별 일일 기록은 이력으로 유지

## 12. 코드 작성 규칙

- 오류를 직접 확인하고 원인을 수정하기 위해 IsValid 사용을 되도록 지양
- 필수 StateTree 바인딩·부모 Task 제공 참조의 누락을 IsValid 분기·조기 반환으로 숨기지 않음. 오류·로그 확인 후 바인딩·생성·초기화 원인 수정
- 무효가 정상적으로 허용되는 선택적 참조·수명 종료 처리만 필요한 이유를 명시하고 최소한의 유효성 검사 적용. 필수 구성 오류를 정상 흐름으로 처리하지 않음
- UPROPERTY의 일반 지정자는 한 줄에 작성
- meta 내부도 항목별로 줄을 나누지 않고 한 줄로 작성
- 길이가 무리하지 않으면 meta까지 전부 한 줄로 작성
- 단순 변수 선언, 계산식, 함수 호출도 충분히 읽을 수 있으면 한 줄 유지
- 형식적인 이유로 짧은 코드를 여러 줄로 분할하지 않음
- 구체적인 최대 글자 수는 정하지 않았음
- 툴팁(주석) 작성의 경우 단문 형태로 작성하고, 마침표 없이 작성
    예시) 플레이어 공격용 함수
