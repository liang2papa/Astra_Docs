1. ABP_NPC_Zombie의 기존 Action Animations → Fire Montages에 **None 키=좀비 공격 몽타주** 등록. 별도 근접 맵을 추가하지 않음. 맨손 플레이어도 같은 None 키, 근접 무기는 Club/Blade 등의 실제 WeaponType 키 사용
2. 공격 몽타주 Slot=DefaultGroup.FullBody, ABP 최종 FullBody Slot 연결. 한 번 재생, 자동 Blend Out 활성. 순환 Section은 사용하지 않음
3. 몽타주는 **공격 시퀀스만** 사용. 접근용 걷기 시퀀스와 Melee_Lunge Notify는 넣지 않음. 접근 시에는 기존 Idle/Walk→FullBody Slot 경로의 이동 ABP가 속도를 읽음
4. 몽타주 트랙에 엔진 **Montage Notify Window** 추가, Notify Name=`Melee_Hit`. 실제 손/날이 타격하는 구간에 배치, 정확히 한 개 필수. 일반 Skeleton Notify나 새 NotifyState 클래스가 아님
5. 근접에는 Weapon_FireCommit을 추가할 필요 없음. 기존 총기 몽타주의 Weapon_FireCommit은 변경하지 않음
6. 창 길이는 양수, 공격 시작과 끝 사이에 배치. Notify Name은 위 문자열과 일치. 몽타주 Notify Window의 엔진 Branching Point 동작 사용

접근 시작 때 선택 방향을 정렬하고, 이후 매 Tick 선택 대상의 현재 위치를 따라 기존 DA 회전속도로 방향 갱신. NPC가 대상을 못 보면 기존 마지막 관측 위치 사용. 거리 경계까지의 남은 간격으로 감속하지 않고 LungeSpeed로 이동하며 누적 거리/시간 한도는 유지. 타격 거리 도달 또는 접근 한도 끝에서 전진 중지→공격 몽타주, 이후 방향 추적 종료. 처음부터 거리 안/플레이어 유효 대상 없음은 제자리 공격 몽타주. 대상 소실·사망·기억 소실·진영 부적합은 기존 취소 정리. 몽타주 정지/잘못된 순환 Section은 모션 길이+Blend Out 기준 기한으로 취소. 임의 재생속도·루트모션·캡슐 설정 변경은 이번 후속에서 수행하지 않음.

타격 구간의 본 평가가 끝난 프레임 사이를 직선 Sweep하는 근사 방식. 매우 빠른 회전 궤적의 곡선·한 프레임 안에 열리고 닫히는 극단적으로 짧은 창까지 완전 복원하는 오프라인 포즈 재표본화는 이번 범위 아님. 실제 타격 구간을 충분한 길이로 지정하고 30/60 FPS에서 손/날 위치·창 경계·빗맞음을 확인. 준비/복귀 구간을 타격 창으로 늘려 누락을 보정하지 않음.

### 사용자 GA·StateTree 호출 계약

최신 사용자 제공 공격 Task의 **실제 연결·수정 지점·Tick 완료 감지와 일반 NPC 연사의 전체 경로**는 [NPC 행동 — 공격 Task Blueprint 구조](NPC%20행동.md#공격-task-blueprint-구조--2026-10-26)에서 관리. 아래는 공통 호출 계약이며 제공된 그래프가 모두 적용된 상태라는 뜻은 아님.

- 구체 GA는 사용자 생성. 기존 AstraWeaponGameplayAbilityBase 기반 GetWeaponComponent와 기존 FireEquippedWeapon/CancelFireWeapon/OnWeaponFireFinished 사용
- Asset Tag=`Ability.Weapon.Fire` 유지. State.Combat.Attacking의 소유/차단, Dead·Stunned·Traversal·Evading·Reloading 등 기존 실행 제한 적용. 근접을 위한 새 Attack 태그 체계 없음
- GA 시작 전에 StateTree Condition에서 CanAttackWeapon 사전 검사. GA가 Attacking 태그를 소유한 후 같은 CanAttackWeapon을 다시 검사하면 자기 태그에 막히므로 실제 시작은 FireEquippedWeapon 호출
- 좀비 Action StateTree는 수납 상태에서 AttackStarted 명령을 받아도 Attack에 진입할 수 있어야 함. 맨손에 Draw·WeaponInHand·무기 Ready 조건 적용 금지. 상하체 포즈 분리와 StateTree 행동 수명은 별개
- 기존 NPC Combat Attack 지속 Task 사용. FireEntered는 기존 EventBus에 게시하여 요청 접수 사실 알림. 근접에는 UpperReady가 필수 아님
- Brain Chase는 기존 Chase 명령과 Request/UpdateChaseMove 재사용. Death는 Critical 우선권. 공격 중 거리 이탈로 Brain이 Chase가 되어도 진행 중 근접 1회는 유지, 새 공격은 정상 거리/시야 검사
- 공격 Pressed는 EntityCharacter에서 소비 후 UpperCommand로 전달. Task에서 같은 Pressed를 다시 소비하지 않음
- 타격 판정·피해·속도 변경·Montage Play를 BP에서 중복 실행하지 않음. 입력 해제는 시작한 단발 근접을 취소하지 않으며 명시적 취소/사망은 기존 취소 경로

```text
NPC Brain / 플레이어 입력
→ 기존 의미 입력 → EntityCharacter의 Pressed 소비
→ Mediator UpperCommand.AttackStarted → 사용자 Attack Task
→ EventBus.FireEntered 게시 → Mediator.TryActivateAbilityByTag(Ability.Weapon.Fire)
├─ 활성화 거부 → Task 실패/대기, 이동·피해 없음
└─ 사용자 GA Activate
   → GetWeaponComponent → OnWeaponFireFinished에 자기 완료 이벤트 바인딩
   → FireEquippedWeapon
   ├─ false → 자기 Delegate 해제 → GA 종료 → Task 실패
   └─ true → 기존 Sequence 전체 실행·쿨다운 잠금
      ├─ 유효 대상이 타격 거리 밖 → 기존 이동 ABP로 제한 접근
      │  ├─ 타격 거리 도달 → 이동 정지 → 공격 몽타주
      │  ├─ 거리·시간 한도 → 공격 몽타주(접촉하지 않으면 빗나감)
      │  └─ 대상 소실/사망/기억 소실/진영 부적합 → 정리 → OnWeaponFireFinished(false)
      └─ 이미 거리 안/플레이어 유효 대상 없음 → 제자리 공격 몽타주
      → Melee_Hit 창: Commit → 평가된 접촉 소켓별 궤적 Sweep → 대상별 한 번 피해
      → 창 종료: 타격 중지 → 몽타주 종료 → OnWeaponFireFinished
      → GA: 자기 Delegate 해제 → 결과 보관 → EndAbility → Task 완료
GA End/명시 취소/사망/Task 강제 이탈
→ 자기 Delegate 해제 → CancelFireWeapon → 기존 Sequence 취소
→ 타격 창 닫기·속도/회전/이동 입력/포즈 갱신 설정 정리, 이미 확정한 피해는 취소하지 않음
→ 현재 Brain 의도로 복귀. HP 0이면 사망 우선, 추격 재개 없음
```

빌드 후 위 연결은 사용자 작업. 정상/허공/이동 타겟 회피/벽/반복 겹침/사망/무기 교체/다중 좀비·기존 라이플/유탄 회귀 확인 필요. C++의 외부 함수 계약 반영과 해당 BP/GA/StateTree 그래프가 실제로 연결됐다는 증거를 구분.

## 확정 범위

- 보스 소환기 우선, 이후 아스트라. 영혼 결속 구현은 아스트라 제작 단계
- 좀비 애니메이션: Idle·걷기·근접 공격, 기존 호환 사망 사용. 상하체 포즈 분리 없음
- 공격 Root Motion 없음. 짧은 빠른 전진 구간과 실제 타격 구간을 분리
- 사용자 추가 지정: 플레이어는 조준점 기반의 가까운 적을 향해 접근. 같은 대상 선정 방식을 추후 아이템 상호작용에도 재사용. 근접 타격 사거리와 돌진 최대 이동 거리는 별도 데이터
- 좀비 생존 수 제한 없음. 누적 개체가 보스 공략을 방해하는 기획 유지
- 보스 사망 시 자신이 소환한 좀비 제거. 전투 정리 제거는 실제 사망 보상 드롭과 구분
- 공격 우선권·동시 공격 수 제한은 검토안. 현재 구현 확정 대상으로 확대하지 않음
- 신규 빌드·UHT·Editor 실행은 별도 사용자 지정 필요

## 실제 누락과 수정 대상

1. **무기 없는 사거리**: NPCAIController.GetAttackRange가 장착 무기 없으면 0 반환. WeaponComponent의 공통 조회에서 무기 수치 또는 비무장 ASC 수치를 읽고 AI는 같은 조회 사용
2. **공격 준비**: UpdateCombatAttack이 무기 Carry Ready·UpperReady·머즐 방향·사선을 공통 요구. 원거리 조건은 원거리에만 적용, 근접은 몸 방향·접근 거리·경로/타격 장애물 검사 사용
3. **실행 진입**: RequestWeaponFire는 HasEquippedWeapon=false 거부. AttackSequenceHandler.StartFire도 WeaponInstance와 AimSolution 전제. 비무장/근접 수행이 이 원거리 전제 때문에 거부되지 않도록 같은 진입 확장
4. **갱신 호출**: EntityCharacter.Tick은 HasEquippedWeapon일 때만 UpdateWeaponRuntime 호출. 무기 없는 근접도 갱신될 수 있도록 조건을 정리해야 함. 새 Component Tick·독립 프레임 타이머를 만들지 않음
5. **실제 근접 전달**: 현재 Astra 공격 Commit은 Ranged 전용. 돌진 이동·타격 Sweep·대상별 1회 피해·취소 정리가 필요. 추가 대조 결과 기존 Sequence/Commit Handler 내부 분기로 수용 가능하므로 새 MeleeAttackHandler를 우선 신설하지 않음
6. **몽타주 선택**: 현재 ABP Actions는 발사/재장전/Mantle/Death 구성. 기존 무기 종류별 맵은 None·Club·Blade 키 사용 가능. 공통 공격 몽타주로 확장하는 방향을 먼저 검토하고, 근접 전용 맵을 같은 목적의 중복 저장소로 추가하지 않음. 현재 Fire 명칭·Notify의 기존 에셋 호환은 구현 시 정리 대상
7. **소환**: 현재 Astra 소환 스킬 공통 실행·생성물 추적은 확인되지 않음. 다만 소환기를 이유로 Attack Facade를 새로 만들지 않음. 공통 GA 시작/완료/취소와 실제 소환 수행의 경계는 근접 중복 점검 후 별도 변경안으로 확정

## 기존 Handler 내부 분기 가능성

**가능. 이번 범위에서는 새 MeleeAttackHandler 신설 없이 기존 두 공격 Handler 확장 우선.** 현재 실행 가능하다는 뜻이 아니라 Source 책임·호출 구조 기준의 수용 가능성 판단.

| 기존 위치 | 근접 분기로 추가할 책임 | 유지할 공통 책임 |
|---|---|---|
| WeaponComponent | 무기 없음=Melee, 장착 시 WeaponData.AttackKind 해석. 비무장/무기 수치 조회·요청 중계 | 외부 공격 API·상태·이벤트, Handler 사이 중계 |
| AttackSequenceHandler | 근접 몽타주 선택, 준비→접근→타격→회복 구간, 제한된 전진 이동·종료 시 이동 정리 | 기존 실행 ID·몽타주 재생·쿨다운·정상/실패/취소·완료 사건 |
| AttackCommitHandler | 근접 공격 확정, 타격 구간 Sweep·벽 차단·동일 실행/대상 중복 피해 방지·구간 종료 정리 | 확정 데이터·피해 전달 사건, 원거리의 기존 투사체/Hitscan/Beam·탄약 처리 |
| 기존 Entity 이동/StateTree 중재 | 접근 중 일반 추격/플레이어 이동과의 소유 충돌 방지 | 기존 이동 실행·사망 우선권. 새 별도 이동 Component 없음 |

- Handler끼리 직접 참조하지 않고 WeaponComponent의 기존 Delegate 중계 경계 확장
- 근접 구간의 전진은 Sequence 책임, 실제 피해 판정은 Commit 책임. 새 Handler나 양쪽에 별도 몽타주·쿨다운 수명 복제 없음
- 현재 StartFire/StartFireMontage/CommitInitialShot은 WeaponInstance·유효한 FWeaponAimSolution 전제. CanCommitAttack/BuildCommitData도 Ranged·머즐 전제. 근접 분기를 해당 검사 뒤에 추가하는 것만으로는 동작하지 않으므로 원거리 전용 선행 조건부터 분리
- FWeaponAttackCommitData에는 현재 AttackKind가 없고 DeliveryType은 PhysicalProjectile/Hitscan/Beam만 존재. 공격 종류와 원거리 전달 방식을 구분하는 실행 데이터 확장 필요. 근접을 가짜 Hitscan·원점 머즐로 가장하지 않음
- UpdateSequence는 현재 충전·원거리 반복 갱신 위주. 근접 구간 갱신을 여기에 추가하고 Commit 구간 갱신은 Facade로 전달. 무기 없는 Entity도 기존 갱신을 호출하도록 조건 정리
- OnPlayMontageNotifyBegin은 이미 구독, End는 미구독. 엔진 Montage Notify Window와 기존 Delegate를 확장해 구간 표현 가능. 같은 목적의 새 Notify 클래스 생성 불필요
- 기존 bFireCommitted/Commit 실패의 의미 분리 필요: 허공 공격·빗맞음은 유효한 근접 공격이며 설정/실행 실패와 다름. 실제 타격 대상이 없어도 공격 수행 후 쿨다운 유지
- WeaponComponent.HandleAttackShotCommitted는 현재 무조건 AccumulateRecoil 호출. 공통 완료·Commit 경로를 재사용해도 원거리 반동·탄약·정확도 보정을 근접에 적용하지 않도록 분리

## 플레이어 맨손·근접 무기와 접근 규칙

| 사례 | 데이터 원본 | 실행 경로 |
|---|---|---|
| 장착 무기 없음 | 기존 Entity ASC UnarmedDamage / UnarmedCooldown / UnarmedRange | 공통 Attack의 Melee 분기, 가짜 WeaponInstance 없음 |
| 근접 무기 장착 | WeaponData.AttackKind=Melee, 기존 무기 피해·쿨다운·EffectiveRange | 같은 Melee 분기, 무기 설정과 해당 캐릭터 몽타주 사용 |
| 원거리 무기 장착 | 기존 WeaponData와 Ammunition | 기존 Ranged 분기 |

- Club·Blade 무기 종류가 이미 EquipmentTypes에 존재. 좀비/플레이어별 별도 공격 Component를 만들지 않음
- 사용자 확정: **타격 사거리와 돌진 최대 이동 거리는 별도 값**. 근접 무기 EffectiveRange 또는 맨손 UnarmedRange를 돌진 거리로 덮어쓰지 않음
- 접근 필요 거리=타격 가능한 위치까지의 부족 거리. 허용 최대 돌진 거리 안에서만 접근, 타겟 중심 관통 금지. 공격 진입 검사와 타격 순간의 실제 Sweep은 별도
- 플레이어 후보 선정은 조준점 기준. 해석안: 조준점 주변의 허용 범위·시야·접근 조건을 만족하는 적 중 우선순위로 선정. 화면상 조준점 거리와 실제 거리의 정확한 점수/동률 기준・대상 교체 안정화는 구현 전 세부 확정 대상
- 사용자 확정: 플레이어의 사정거리 내에 유효한 타겟이 없으면 이동 보정 없이 제자리 공격. 타겟 참조 없음만으로 공격 시작을 거부하지 않음. 정상 몽타주·타격 구간·쿨다운 수행, 실제 피해는 타격 구간 충돌 결과로 판단. NPC의 타겟 필요 조건과 구분
- NPC는 기존 인식/기억의 타겟을 전달. 플레이어의 조준점 점수와 NPC의 감지 판단을 실제 공격 실행부에 혼합하지 않음
- 플레이어의 카메라 원점/방향 제공 API는 존재하나 AimHandler는 현재 Ranged·WeaponInstance·Muzzle을 전제. 이 기존 총기 조준 Trace를 그대로 맨손/상호작용 후보 선정기로 사용할 수는 없음
- 현재 InteractionDefines에는 상호작용 종류만 존재, WorldItemActor.TryPickup은 실제 획득 실행 경계. 확인한 Source에서 공통 조준점 후보 선정 구현은 없음. 대상 선정 규칙을 공유하고 공격/상호작용의 대상 필터·허용 거리·실행은 분리. 향후 상호작용에 자동 접근까지 적용한다는 의미로 확대하지 않음
- 조준점 대상 선정은 공유 기능으로 설계하되 구체 클래스/소유자 신설은 기존 입력·Context·인터페이스와의 연결 검토 후 결정. 이번 점검만으로 새 타겟팅 Component/Subsystem 구현 없음
- 플레이어 근접의 수용 설계는 반영하되 기존 프로토타입의 플레이어 근접 무기 제작 제외를 임의 변경하지 않음. 현재 좀비 제작과 플레이어 콘텐츠 제작 범위 구분

## 최소 변경안

```text
기존 Attack Task → Mediator → 사용자 GA_Attack
→ 기존 WeaponComponent 공격 API
→ 기존 AttackSequenceHandler: 몽타주·공격 순서·쿨다운·완료/취소
   ├─ 원거리 구간 → 기존 Commit 요청 → Facade → AttackCommitHandler.Ranged 분기
   └─ 근접 구간 → 제한된 접근 이동 → Facade → AttackCommitHandler.Melee 타격 구간
→ 기존 WeaponComponent 완료 사건 → GA 종료 → Task 결과
```

- 새 EntityAttackComponent·MeleeAttackHandler 신설 없이 기존 Sequence/Commit Handler 분기 확장 우선
- 기존 Sequence의 Montage Notify Begin/End 경계를 활용 검토. 엔진 Montage Notify Window로 구간을 표시할 수 있다면 같은 목적의 새 Notify 클래스 생성 불필요
- 정상: 공격 종료 → 돌진 속도/입력·타격 판정 정리 → 기존 완료 사건 한 번 → 현재 Brain 의도 선택
- 실패: 필수 몽타주/설정 누락·공격 불가 → 시작 실패 반환, 이동·피해 없음
- 취소/사망: Sequence의 기존 취소 경계 → 근접 수행 정리 → 기존 결과 경로. 과거 추격 경로 강제 복구·사망 후 이동 재개 금지
- 후속 확인: 기존 라이플/유탄·충전·쿨다운·멀티 NPC Handler 소유권·사망 경로 회귀
